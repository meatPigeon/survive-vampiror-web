# Horde encounter

This is the deliberately small first native web slice: one arena, forty permanent zombies and one knight. The Godot sibling is a rules/art reference, not a dependency. Its current WASD movement, 30-HP zombies, automatic 4-damage bites and 15-damage warned sweep informed the port. The single knight has slice-specific health and no later attack phases. Three waves, temporary recruitment, perks, audio and backend rewards are outside this slice; do not imply full Godot feature parity.

`horde` replaces `mini-game` in the local composition. The unused starter folder and registry fingerprints are kept as references to the seeded catalog source. The existing base remains responsible for sign-in, lobby and shared UI. This encounter uses local simulation state and does not report arbitrary scores, quest completion or grant platform currency; those need a separately scoped integration and real configured IDs.

The simulation is deterministic and separate from Three.js. Keyboard, touch and the bounded agent movement action feed the same direction read by the fixed-step controller. Releasing movement stops the commanded motion. The first movement starts combat; pause/focus loss clears held input. Host suspension stops RAF and removes listeners, preserving the encounter for return from the lobby. Restart creates a fresh encounter, including all health, casualty state and timers.

Both bundled GLBs are user-owned assets copied from the sibling's `assets/characters/`. They retain idle/run animations and are cloned with SkeletonUtils for independent rigs. Vite fingerprints them and emits relative asset URLs so staged version paths work. The scene's ready promise waits for these assets, and capture renders immediately before reading the WebGL canvas. Keep the public, JSON-safe `ctx.exposeToAgent` state and the real-input movement action when extending the canvas.

Crowd separation alone compresses units against bounds; repeated body exclusion solves the pairs at corners and around the knight. Keep all four corner scenarios in the gameplay tests when changing movement. Combat tests cover warned damage, rear exclusion, pause, win/loss through ordinary movement, and terminal-state stability. `npm run check` and the staged upload both run the gameplay tests. Browser inspection is still needed for models, controls and host lifecycle.
